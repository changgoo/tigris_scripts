TIGRESS-NCR on stellarai-amd

Which compiler, MPI library and compiler flags run the 8 pc TIGRESS-NCR models fastest on the AMD Zen 5 nodes of stellarai-amd, and why. Six module stacks and nineteen flag variants, measured on the production checkpoints. Each one restarts the same state and advances 200 cycles. The stack comparison was re-measured on 2026-10-04 with the NaN-safe production flags and the new default ray-tracing termination test.

Recommendation

Build with GCC 14 + Open MPI 5.0.10 (gcc), the default in stellarai-amd/env.sh and the production scripts since 2026-10-05. It's the fastest stack: tied with GCC + Intel MPI (gcc-impi) on MHD and 9% faster on CRMHD. build_tigress.sh picks it, with its benchmarked flags, when you don't pass --cc; CC=gcc-impi is a good fallback.

cd ~/tigris_scripts/tigress_ncr
bash build_tigress.sh --machine=stellarai-amd --physics=mhd   --worktree=ncr-cr-coupling
bash build_tigress.sh --machine=stellarai-amd --physics=crmhd --worktree=ncr-cr-coupling

The production jobs' snapshot step loads the gcc-impi modules, because pyathena's mpi4py is linked against Intel MPI and aborts in MPI_Init under Open MPI.

What was measured

Both workloads are 8 pc production checkpoints from Stellar: a 1024 × 1024 × 6144 pc box on a 128 × 128 × 768 mesh (12.6 million cells) with 32³ meshblocks, which gives 384 blocks. That is one MPI rank per block, no OpenMP, so exactly 4 full nodes.

  • MHD + NCR: mhd-ncr-8pc/TIGRESS_NCR.00006.rst at t = 300, cycle 646 619, with ray tracing, NCR photochemistry and FFT self-gravity.
  • CRMHD + NCR: crmhd-ncr-8pc/TIGRESS_NCR.00003.rst at t = 150, cycle 1 250 001, with cosmic-ray transport coupled to NCR (cr/photchem_flag=1) and dt = 1.2 × 10⁻⁴.

Each run restarts the checkpoint unchanged and advances 200 cycles. The time per cycle comes from the code's own loop timers (TIGRESS_NCR.loop_time.txt, one line per 10 cycles), averaged over ranks, with the first partial window dropped. Start-up, restart reading and the final dump are excluded. The timers split each cycle into the time integrator (hydro/MHD/CR), ray tracing, self-gravity, photochemistry and the operator-split tasks.

Repeated runs of one build agree to about 0.5–3%, so differences under about 2–3% are ties.

With the new termination test, the compiler decides

Why Open MPI used to be 4× slower

Ray tracing passes photon packets between ranks with asynchronous point-to-point messages (MPI_Iprobe, MPI_Isend, MPI_Testsome). Until PR #348 it detected that every ray was done with MPI_Fetch_and_op on a one-sided window on rank 0, which every rank polls. With Open MPI 5.0.10 (UCX) that check alone took 2.5 s per ray trace, against 0.08 s with Intel MPI, so a cycle took 1.16–1.23 s. Changing Open MPI's one-sided and point-to-point components didn't help, and neither did rank placement (table below, 2026-10-02/03). The comm-loop timers showed the cause; replacing the counter with a nonblocking allreduce (<ray_tracing>/termination = iallreduce, now the default) made Open MPI as fast as Intel MPI and left Intel MPI unchanged. Details: ray-tracing termination test.

Compiler flags

configure.py's --cxx presets add flags of their own. For example, g++-simd adds -march=native, and icpx adds -xhost, which builds a binary that refuses to run on AMD. So the presets are no longer trusted. Each toolchain in env.sh carries a complete flag set, and build_tigress.sh writes it over the Makefile's CXXFLAGS, for both compiling and linking. To pick those sets, 19 variants were built for both physics, all with Intel MPI so that only the compiler changes. The best few were then repeated until each had 3 runs. This sweep ran on 2026-10-02/03, before the NaN-check rule below; its fast-math variants used plain -ffast-math and icpx's winner was -fp-model=fast=2.

NaN checks (2026-10-04). Plain -ffast-math and icpx -fp-model=fast=2 let the compiler assume that NaNs never occur, so every NaN test in the solver (C2P floors, CR-FOFC and CRAverage flags, the NCR bail-out) compiles to false. Production flags therefore add -fno-finite-math-only for GCC and AOCC and use -fp-model=fast for icpx, and build_tigress.sh refuses flags that remove NaN checks. For GCC this costs nothing measurable. AOCC loses 15–20% in photochemistry, and icpx loses the 14% CRMHD gain that fast=2 gave.

Correctness

Every run of one physics ends at the same simulation time, so the final rows of the history file can be compared (bench/compare_hst.py). The comparison has to allow for one fact: these runs are not bitwise reproducible, even with one executable. Ray tracing, cosmic rays and feedback depend on MPI message order. So each build is compared against the spread between repeats of the reference build.

The CRMHD history has three NaN columns in every run, including the strict -O3 and icpx precise builds, and the 2026-10-04 builds with NaN checks kept. They come from the code or the state (probably an average over an empty set), not from the compiler. They are worth a look in the source, separately from this benchmark.

Reproduce or extend

Everything is on the main branch of tigris_scripts, in tigress_ncr/; this page's source is bench/reports/toolchains-stellarai-amd.html. bench/BENCHMARK_SPEC.md is the step-by-step procedure for another machine, and bench/results/stellarai-amd.txt holds every run.

# one run, or the whole stack matrix, or the flag sweep
bench/submit.sh stellarai-amd mhd gcc-impi 200
nohup bench/run_matrix.sh stellarai-amd 200 2 > bench/logs/matrix.log 2>&1 &
nohup bench/flag_sweep.sh stellarai-amd 200 1 > bench/logs/sweep.log 2>&1 &
python3 bench/summarize.py bench/results/stellarai-amd.txt
Checkpoints: /projects/EOSTRIKE/tigris-benchmark (staged to /scratch/gpfs/EOST/$USER/tigris-benchmark). Timers are rank means of the code's loop timers; “other” is the remainder of the cycle (new dt, particle bookkeeping, synchronization).
