Production builds

Each machine's env.sh holds the winner as DEFAULT_TOOLCHAIN with its complete flag set, so build_tigress.sh uses it when you don't pass --cc. The build refuses flags that remove the NaN checks (bench/nan_check.cpp). On Athena, load_toolchain also exports FI_MR_CACHE_MONITOR=memhooks, which makes self-gravity 3.8× faster (see below).

Where the time goes on each machine

  • MHD is dominated by ray tracing on every machine (44–60% of the cycle). It is limited by point-to-point message latency, so the network and MPI library matter as much as the cores.
  • CRMHD traces rays rarely and is compute-bound: the integrator (CR transport included) is about half the cycle everywhere, and NCR photochemistry is the next-largest piece.
  • Athena runs 192 ranks per node on 2.4 GHz Zen 5c cores, so its integrator is 1.6× slower than stellarai-amd's 4.8 GHz Zen 5 at 96 ranks per node, and its ray tracing is 1.4× slower.

Athena charges by the node (a Turin node-hour is 12.19 SBUs), and per node it is the cheapest machine, 25–27% under stellarai-amd. Per core it comes second: a Turin node has 256 cores and the run uses 192 of them, so Athena spends about twice the core-hours of stellarai-amd, but 7–13% fewer than Tiger and 14–29% fewer than Stellar. On 4 nodes Athena runs 1.25–1.33× faster per cycle but costs 1.5–1.6× more, so the production scripts use 2 nodes. For wall-clock time per cycle, stellarai-amd is fastest by a wide margin.

Self-gravity was 3.6× slower on Athena than on stellarai-amd at the same layout, while the integrator stayed within 10%. A per-phase profile put 94–98% of the gap in the six fftMPI remaps of each solve, and fftMPI's point-to-point and all-to-all modes were equally slow. OSU benchmarks found the cause: for 4–64 KB messages each Slingshot NIC sent only ~230K messages/s, so a 192-rank all-to-all of 4–16 KB took 42 ms, against line rate from 4 KB on stellarai-amd. The executables load the OS libfabric (2.6.0), whose default memory-registration cache monitor, userfaultfd, behaves like no cache at all: FI_MR_CACHE_MONITOR=disabled is exactly as slow.

The fix is FI_MR_CACHE_MONITOR=memhooks. It makes the gravity solve 3.8× faster, as fast as on stellarai-amd, and brings OSU to line rate from 4 KB (alltoall 3.5 ms at 16 KB). HPE's own libfabric 2.3.1 does the same. Athena's env.sh exports it in load_toolchain, and the tigress_classic Athena scripts export it too. Ruled out on the way: the compiler, the FFT library (MKL's FFTW3 interface), MPICH_ALLTOALLV_THROTTLE, MPICH_SMP_SINGLE_COPY_MODE, MPICH_OFI_NIC_POLICY, FI_CXI_RX_MATCH_MODE, MPICH_SHARED_MEM_COLL_OPT and the CXI rendezvous settings.

Sparse gravity. gravity/solve_grav_hyperbolic_dt=true solves self-gravity once per MHD time step instead of every cycle, as the tigress_classic CR runs do. With memhooks it cuts Athena's CRMHD cycle only from 0.278 to 0.260 s (−6%; it was −22% before the fix), with histories inside the run-to-run envelope. It is off by default and turned on with qsub -v SPARSE_GRAV=1.

The Open MPI penalty came from the rank-0 MPI_Fetch_and_op counter that every rank polled to detect that all rays were done. Since <ray_tracing>/termination = iallreduce became the default, the library no longer matters on stellarai-amd. Stellar and Tiger have not been re-measured with it; Intel MPI was fast with either method on stellarai-amd (0.283 s both ways), so their production numbers should hold. For CRMHD, which traces rays rarely, the libraries were within 3% on every machine.

The compiler follows the CPU vendor

  • Intel CPUs. icpx wins both physics. On Stellar, GCC 13 takes twice as long in NCR photochemistry. On Tiger, GCC 11.5 ties icpx.
  • AMD Zen 5 and Zen 5c. GCC 14 wins on both machines. AOCC is 7–16% slower, mostly in photochemistry (-fno-finite-math-only costs it 15–20% there), and icpx is 18–40% slower for CRMHD. icpx's -x<cpu> builds refuse to run on AMD, so it uses -march=znver5.
  • Cray CCE 20 on Athena is 3–6× slower, all of it in NCR photochemistry, and it miscompiles: its MHD time step departs from the other compilers by cycle 10, and 35–39 CRMHD history columns are off.

Correctness and known issues

Runs are not bitwise reproducible even with one executable, because ray tracing, cosmic rays and feedback depend on MPI message order. So each build's final history row is compared with the spread between repeats of its machine's reference build (bench/compare_hst.py).

Open items

  • Athena's libfabric default. Solved in our scripts with FI_MR_CACHE_MONITOR=memhooks; a draft ticket for NAS support (athena/nas_ticket_mr_cache_monitor.md) asks about the system default, which affects every code that sends many medium-size messages.
  • Stellar and Tiger predate the iallreduce termination and the NaN-safe GCC flags. Their production builds (icpx-impi) should not change, but a short re-run would confirm it.
  • NaN history columns. Every CRMHD history from the restart checkpoint has NaN columns on every machine and compiler: 3 on the Princeton machines, 9 on Athena, whose production-diagnostics source adds floor and ceiling columns for the passive scalars. A fresh start has none, so they come from the checkpoint's state.
  • Sparse gravity now saves only 6% of a CRMHD cycle on Athena, where gravity is as cheap as on the Princeton machines. It stays off by default.
  • GCC 11 and 13 don't link ncr-cr-coupling with LTO (undefined reference to Accretion::rctrl). The fix is one line in src/particles/accretion.cpp: constexpr int Accretion::rctrl;. GCC 14 and icpx are not affected.
  • Tiger rack groups. MHD runs on tiger-i* nodes were 6–7% faster than on tiger-g* nodes, and Slurm offers no way to ask for one group. Gaps under ~4% on Tiger need a node-list check.

Reproduce

Everything is in tigress_ncr/ of tigris_scripts: bench/BENCHMARK_SPEC.md is the procedure for a new machine, and bench/results/<machine>.txt holds every run.

bench/submit.sh <machine> mhd <toolchain> 200          # one run (Slurm)
nohup bench/run_matrix.sh <machine> 200 1 &           # every module stack
nohup bench/flag_sweep.sh <machine> 200 1 &           # flag variants
bench/pbs_submit.sh athena --workload=rst mhd:gcc crmhd:gcc --submit   # PBS (Athena)
python3 bench/summarize.py bench/results/<machine>.txt
Checkpoints: /projects/EOSTRIKE/tigris-benchmark (mhd-ncr-8pc/TIGRESS_NCR.00006.rst at t = 300, crmhd-ncr-8pc/TIGRESS_NCR.00003.rst at t = 150). Timers are rank means of the code's loop timers; “other” is the remainder of the cycle (new dt, particle bookkeeping, synchronization). Report source: tigress_ncr/bench/reports/toolchains-all-machines.html.
